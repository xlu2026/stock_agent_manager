# 平台发布（公众号之外）

> 账号矩阵、导出流程与发布记录。当前只接知乎；**导出可以自动，发布永远人工**。

## 1. 原则

- **导出可自动，发布不可自动**：`writing/export.py` 只写文件，不联网、不读平台凭据、不调浏览器。
  发布、原创/转载声明、AI 标注都由人在平台后台完成。这条与公众号同源，见 [AGENTS.md](../AGENTS.md)「对外表达」。
- **一稿多版**：公众号版和知乎版从同一篇 canonical 文章派生，但不是复制粘贴——front matter、H1、
  内联样式都要按平台去掉或换掉。
- **合规扫两遍**：`writing/article.py` 渲染时一遍，导出时 `writing/platforms/zhihu.py` 再跑一遍
  `article_compliance`；不过就拒绝导出，和写草稿的闸门一致。
- **不存平台凭据**：知乎没有可用的发布接口，导出不需要登录态；不要把 cookie / 密码写进仓库或对话。

## 2. 平台矩阵

| 平台 | 流量逻辑 | 最适合哪类稿 | 主要代价 |
|---|---|---|---|
| **知乎**（专栏 + 问题回答） | 搜索长尾 + 问题容器 | 方法论、失败记录、架构权衡 | 金融话题审核严；技术长文不是主品类 |
| **掘金** | 站内推荐（约 48 小时窗口）+ 开发者搜索 | 工程实现：MCP 工具面、三段式下单、确定性引擎 | 前端浓度高；标题带"策略/收益"易触发审核 |
| **少数派** | 编辑推荐 + 长文阅读 | 工具选型、单人工作流、项目复盘 | 投稿制、周期长；代码要收敛 |
| **InfoQ 写作社区** | 编辑把关 + QCon 背书 | 架构决策、工程权衡 | 流量小，价值在背书 |
| **CSDN / 博客园** | 搜索引擎长尾 | 已发文章的镜像全文 | 社区信号弱；适合吃搜索流量，不适合经营读者 |
| **V2EX「分享创造」** | 一次性的同行讨论 | 项目开源、求批评 | 不沉淀内容 |
| **语雀** | 文档站，无推荐流量 | 系列文集 / 索引 | 不是分发平台 |

不建议：雪球/东财（受众预期是标的和观点，与"不荐股、不展示个股代码"冲突）、今日头条/百家号
（机制反向筛选技术长文）、小红书（长文和代码块不适配）。一键分发工具也不建议：各平台排版、
外链、合规规则不同，同步内容容易被判低质。

## 3. 知乎发布 SOP

顺序上**公众号先发**（原创声明按微信规则通常要求首发），知乎在 24–72 小时后跟进。
一稿两版：公众号版保留 front matter 与内联样式；知乎版去掉 front matter 和 H1，标题放知乎的独立字段。

1. 跑导出（见下一节），拿到 `.zhihu.html`、`.zhihu.md`、`.zhihu.json`。
2. 打开知乎 → 创作中心 → 写文章；有专栏就发到专栏「杂灵根散修录」。
3. **标题**用 `.zhihu.json` 里的 `title`；正文先粘 `.zhihu.html` 的内容。
4. 检查行内代码、加粗、引用块、分割线；格式丢了再改用 `.zhihu.md`，仍不对就手工排版。
5. 上传封面（`cover` 字段），按编辑器提示裁；现有封面是 2.35:1，可能需要重裁。
   有单篇专用封面的（如开篇 `cover-opening-2.35x1.png`），导出器优先用它；没有再落到栏目封面。
6. 选话题（`topics` 字段，最多 4 个），不要一篇塞十个。
7. 按知乎规则标注 AI 辅助创作；原创/转载按后台实际选项。
8. 发布后把 URL 回填到 `.zhihu.json` 的 `canonical`，并在本文第 6 节记一行。

> 2026-11-09 已实测（开篇）：HTML 粘贴后段落、分割线正常；行内代码/加粗/斜体仍要按编辑器实际微调。
> 导出成功不等于格式没问题，第一次发仍要自己看一眼。
>
> 文末 `本文首发于公众号「杂灵根散修录」` 现在由导出器自动加；源文已含这句的不重复加。

## 4. 导出命令

```powershell
# 全部文章
python -m writing.export --all

# 指定一篇；--json 输出完整元数据（文章在写作工作区）
python -m writing.export C:\AI_workspace\wechat_writing\articles\2026-11-08-factor-to-backtest-001.md --json

# 换输出目录（默认 output/articles/zhihu/）
python -m writing.export --all --out-dir output\articles\zhihu
```

> `--all` 会扫写作工作区 `articles/*.md`，包括 11-07 的两篇旧稿；正式发布用显式路径，
> 别一把梭把旧稿也导出去。

产物（每篇三个文件）：

| 文件 | 用途 |
|---|---|
| `<date>-<slug>.zhihu.html` | 粘进知乎编辑器的正文（语义 HTML，无内联样式） |
| `<date>-<slug>.zhihu.md` | 存档 / 兜底（HTML 粘贴失败时用） |
| `<date>-<slug>.zhihu.json` | 元数据：标题、话题、封面、canonical、发布状态 |

`.zhihu.json` 的字段：

| 字段 | 说明 |
|---|---|
| `source` / `source_sha256` | 源文章路径与指纹；指纹变了说明源文改过，应重导 |
| `topics` | 按栏目 + 标签映射的话题建议，最终以知乎搜索为准 |
| `cover` | 栏目封面路径；没有就是 `null` |
| `canonical` | **人工回填**的知乎文章 URL |
| `published_at` / `published` / `status` | 人工回填；`status` 从 `exported` 变 `published` |
| `publish_api` | 固定 `absent`：导出层没有发布能力 |

**重导出用 merge，不整份覆盖**：`canonical`、`published_at`、`notes` 会保留，`status: published`
不会被降级。这和公众号 `draft/update` 整篇覆盖会冲掉手动勾选是同一类坑。

## 5. 平台差异（公众号 vs 知乎）

| 项 | 公众号 | 知乎版 |
|---|---|---|
| front matter | 保留（机器契约） | 删除 |
| 标题 | H1 + 后台标题 | 只留后台标题，正文删 H1 |
| 刊头 | `*杂灵根散修录 · 量化研究 001*` | 保留，当系列标记 |
| 导语 | summary 引用块 | 保留；信息流只露前两行 |
| 代码 | 内联样式 HTML | 行内代码需在编辑器里手动设样式；长代码给仓库链接 |
| 外链 | 正文不可点 | 可点但降权，只放 repo / 实验记录 |
| 文末 | 实验 ID + 风险提示 | 逐字保留；末尾自动加首发句（源文已有则不重复） |
| 封面 | 2.35:1 素材 | 按编辑器提示重裁 |
| 话题 | 公众号标签（弱） | 知乎话题决定推荐 |
| 发布 | 人工 | 人工 |

实现上刻意不复用 `writing/wechat.py::markdown_to_wechat_html`：那套带公众号内联样式，知乎会剥掉
`style`，留着反而干扰。知乎用独立的语义渲染（`h2` / `p` / `strong` / `blockquote` / `code`）。

## 7. 边界与坑

- **不用知乎「关联账号」自动同步**：绑定后默认开启内容同步，审核后**自动发布**，绕过人工复核、
  AI 声明、封面与话题；打开「历史内容同步」还可能把旧文一起补发。它不提供草稿箱，也不适合
  这个号"每篇人工点发布"的流程。要省事就手动粘一次，别把发布权交给平台规则。
- **不做发布**：导出层没有 `freepublish`、没有浏览器自动化、没有网络客户端；测试会扫源码。
- **不存状态在 front matter**：`writing/article.py` 的 render 是确定性的，一重渲染就冲掉；
  发布状态放 `.zhihu.json` 或本文第 6 节。
- **知乎审核**：标题和话题避开"推荐/买入/年化收益"这类词；合成数据声明和风险提示不要删。
- **导出文件是派生物**：`.zhihu.html` / `.zhihu.md` 可随时重生成；`.zhihu.json` 里的手填字段才是状态。
