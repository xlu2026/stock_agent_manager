杂灵根散修录 · AI技术 003

一个看起来像好消息的答复

我发出去的问题很短：策略能在这个终端里跑，能不能让外面的程序调它？

答复也短：策略可以在本地运行，运行的时候不能读本地文件，也不能接外部信号。

我第一遍读，只看见前半句。能用，就先跑起来试试。

三种「能跑」不是一回事

摆在一起看，其实有三件事。

第一件，终端里能写策略。界面上有一个 Python 入口，写几行，算一条均线，跑一段回测。这一层是给人看的。

第二件，能从终端导出数据。跑完把结果导成表，或者复制一段文本回本地。这一层是单向的，从里到外。

第三件，能被外部程序调用。外面的脚本按时间把数据推给它，它算完把结果推回来。这一层要双向。

前两件我都有。第三件没有。

我原来以为「能跑 Python」是一个开关，打开之后三件事一起到位。实际只有第一件是终端已经替我准备好的。

边界在哪一行

我原来以为边界在语法或者性能上。它在运行环境：它跑起来的时候能看到什么、能碰到什么，是写死的。

读不到本地文件，我的数据就进不去。接不了外部信号，它算完的结果就出不来。

两头都断，中间那段 Python 只在它自己的框里成立。

所以这条边界可以写成一句：终端里的 Python 是终端的一个功能。通道要让两头都通，这里两头都断。

为什么这条边界合理

刚看到答复时我以为是限制。放了两天，觉得它更像一种分工。

终端要对账户负责。一个能随便读文件、随便发网络请求的运行环境，出事的时候没人分得清是策略写的，还是环境给的。

内嵌 Python 的用途就在原地：算指标、画图、验证想法。这几件事都不需要往外伸手。

范围收得越窄，敢放人进来写代码的空间就越大。

对架构的影响

最直接的一条：我不能把「策略在终端里跑通」当成上线前的一步。

分工得拆成两块。终端那块负责验证想法，同一段逻辑写进去，看它在给定数据上怎么走。外面那块负责取数、拼信号、留记录，都在我自己的机器上。

两块之间先靠人接。参数抄过去，结果抄回来。慢，但每一步都看得见。

真要往自动化走，先要解决的是数据怎么进、信号怎么出。策略写得漂不漂亮，在这里排不上号。

我这种散修本来就没有一条完整的路。手里几段能用的工具，接缝处自己补。

先把边界写下来，再谈快慢。
