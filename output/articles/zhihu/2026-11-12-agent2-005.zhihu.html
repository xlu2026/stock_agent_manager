一个顺手就坏的方案

原来的方案是把拉数和回测放在一个 agent 里。一个 agent 会拉数、会跑回测、会写报告，配置看着简单。

跑起来第一个出问题的地方是工具列表。它手里既有点鼠标的，也有搬数据的。我让它看一段最近的数据，它可能去跑回测，也可能去拉数，取决于它当场怎么理解这句话。

拉数本身不轻。要起任务，要轮询，失败了要重试。这些等待都算在回测 agent 的会话里。会话一长，前面的上下文被挤出去。

决定性的一次是出错的时候。它报一句失败，我分不清是数据没拿到，还是策略代码写错了。两种情况报同一句话，只能从头翻日志。

拆开之后各管什么

现在这条链路是三个 agent。

Agent 1 管研究和回测。它不碰数据源，只读已经落好的快照。

Agent 2 只管取数。它的活是把外面的数据搬回本地，摆整齐，再告诉别人放在哪。

判断留在我这里。哪份数据能用、结论算什么，这两件事不交给 agent。

工具面互不重叠，出错的位置就能分开。

六个工具与一条铁律

Agent 2 只挂 6 个数据工具。没有回测工具，没有下单工具，也没有 shell。

工具面窄，动作空间就窄。指令写错的情况，它最多拉到错的数据，不会顺手动别的东西。

铁律只有一条：不覆盖旧快照。每次刷新新建一个目录，旧的原样留着。

定这条规则的原因是要能回到上一份数据。刷新到一半失败，新目录是半成品，旧目录还在，一个字节没动。两边可以对着看，也可以直接回退。

后台作业为什么要轮询

拉数是长作业。发起之后不会马上有结果，接口先返回一个 job_id。

之后去轮询，看它有没有到 succeeded。这一步多了一次查询，作用是把「还在跑」和「跑挂了」分成两件事。

让 agent 在原地等，会话就卡在等待里。拆出 job_id 之后，等待变成一件可查的事，不占会话。

latest 指针

快照成功之后，Agent 2 写一个 latest 指针，指向新目录。

Agent 1 只认这个指针。它不需要知道今天的数据叫什么名字，也不需要知道昨天那份放在哪。

指针只有一个，下游读同一处。要回滚，把指针改回上一个目录，数据文件一个都没动。

一份快照落到哪里由指针记账，比在多处各记一遍可靠。

分工的收益

拆完跑了一段时间，收益不在速度上。

收益在出错的时候。数据没到，去看 Agent 2 的 job_id 状态。回测结果不对，去看 Agent 1 的代码。两边不用互相解释。

第二件事是会话长度。等待、重试、长任务留在 Agent 2 那边，Agent 1 的上下文只装研究本身。

分工先解决归因，效率不是这一步的目标。

三个 agent 各守一段路，我在后面记账。哪一段塌了，我知道去哪儿补。
